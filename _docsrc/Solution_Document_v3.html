1. Executive Summary

The existing YES ERP captures the material and financial side of every job — Purchase, GRN, Material Issues, Expenses and Sales Invoice all post against a single Job Code. What it does not yet capture is technician time (labour). As a result, job cost is understated, service efficiency cannot be measured, and true job profitability cannot be calculated.

WisdomIT proposes a Technician Time Management Module that plugs into the existing ERP. It adds one new transaction — Time Booking Posting — plus the supporting masters needed to value that time. Time is booked at Task level: one Work Order has one-to-many tasks (e.g. Disassemble, Assemble, Testing), and each booking is keyed by Job No + Task. Because every booking carries the same Job Code, labour joins material, expense and revenue in the job picture, and is posted to Finance using the Job Code (FITD_TA_CODE1) and Technician Code (FITD_TA_CODE2).

The module delivers: accurate labour cost on each job; automatic Normal/Overtime classification; Industry & Location-based labour rates; task-level Standard Hours; and efficiency, productivity and performance reporting against the manufacturer "standard hours" and the 192-hour monthly benchmark. Delivery is staged into Phase 1 (this proposal) and Phase 2 (future billing).

3. Requirement Understanding & Scope

Based on the requirement document and subsequent client confirmations, the work is staged into two phases. Phase 1 combines parts A and B and is delivered together.

Phase 1 — Task-level Time Booking, Costing & Performance This proposal

1A · Time Booking & Posting

  • Capture technician time bookings against the Work Order at Task level, and generate efficiency & productivity reports by Technician, Location, Work Type and Industry.
  • New fields: Work (Job) Type including "Non-Chargeable" (treated as expense using the COGS / cost rate); Transaction Start Date-Time and End Date-Time; Elapse Time (calculated); Time Type (calculated — before/after duty timings and weekends = Overtime, else Normal).
  • Industry Code mapped from the Customer (by Customer number); interim mapping provided via file.
  • Labour Rate applied by Industry and Location; interim rates provided via monthly dump file.

1B · Performance Dashboard & Standard Hours

  • Technician Performance Dashboard for Service Operations and Executive KPIs.
  • Record Standard Hours at Task level, shared by equipment dimensions (Manufacturer · Model · Series · Component · Task).

Task level (client confirmation)

  • One Work Order has one-to-many tasks; time is booked at the task level.
  • Standard time reference is held at task level, shared by Component, Model, Series, Manufacturer.
  • Job Number + Task form the concatenated key for a booking.
  • Example: Recondition Transmission → tasks Disassemble, Assemble, Testing.
  • The client will review the master tables and provide the required inputs; Labour KPI and formulation will be provided in the interim.

Phase 2 — Billing on new platform Future

  • Today service is charged as fixed price for labour repair. In future: both Fixed Price and Time & Material for booked hours on the job.

5. Proposed Solution — Overview

A self-contained module that sits alongside the existing ERP and reuses its masters. The design principle is simple: the Job Code is the common key. Time bookings stamp the Job Code just like GRN, Issues and Expenses do, so they roll up together automatically.

GRN + Material Issue + Expense + Technician Time (NEW) = Job Cost
Job Cost  vs  Sales Invoice (Revenue) = Job Profitability

Time booking follows a three-level structure, with the Task as the bookable level:

LevelHolds
Work Order (Header) — oneJob No, Customer, Equipment (Mfr · Model · Series · Component), Industry, Location, Work Type, Job Status
Task (bookable level) — manyTask (from Task master), Standard Hours (auto), key = Job No + Task
Time line — many per taskTechnician, Skill, Start/End, Lunch, Net Hrs, Time Type, Rate, Labour Cost

No change is required to how material or expenses are entered. The module only adds the missing labour input and the reporting that becomes possible once labour exists.

6. Solution Architecture

Front-endASP.NET 4.8 Web Forms (.aspx), styled to match the current YES ERP theme; server-side validation; same authentication / role model.
Back-endOracle Database — new TM_* tables, views and PL/SQL packages for calculation & posting; foreign keys to existing Job, Employee and Customer tables.
Business logicElapse / Net-hours / Time-Type / Rate / Cost computed in PL/SQL (and re-validated in the app layer) so results are consistent across UI and reports.
Finance postingLabour cost is posted against the Job using Job Code in FITD_TA_CODE1 and Technician Code in FITD_TA_CODE2; the time line additionally carries the Task. No separate cost-center mapping required.
IntegrationReads existing Work Order, Employee, Customer and Supplier masters; writes labour cost to the job.
Interim dataImport screens for the monthly Customer→Industry mapping, Labour Rate dump, and Task Standard Hours files until these are maintained natively.
ReportingServer-rendered grids + export; KPI dashboard summarising bookings (the "pivot-table" diagnostic view).

8. Business / Calculation Logic

ItemFormula / Rule
Elapse TimeEnd Date-Time − Start Date-Time
Net Labour HoursElapse − Lunch Break
Time TypeOvertime if before/after duty timings or weekend/holiday; otherwise Normal
Task Standard HoursLooked up by Manufacturer · Model · Series · Component · Task (with fallback)
RateLabour Rate Master by Location × Industry × Time Type (OT × multiplier); same for all technicians
Labour CostNet Hours × Rate (Cost Rate for non-chargeable, Charge Rate for billable)
Labour EfficiencyTask Standard Hours ÷ Actual Hours (>100% = ahead of cheat-sheet)
UtilisationBooked Hours ÷ 192-hr monthly benchmark
Loss / Idle TimeRecorded against management to surface allocation gaps (not technician penalty)

10. Assumptions & Dependencies

  • Customer→Industry mapping, monthly Labour Rate values, and Task Standard Hours are supplied by the client (file-based) until maintained in the masters.
  • Tasks and their standard hours (by Manufacturer · Model · Series · Component · Task) are provided by the client; the standard-hours lookup precedence/fallback is confirmed during setup.
  • Existing Employee master provides technician number, name and (where available) skill level.
  • Duty timings, weekend rule, holiday calendar and the available-hours benchmarks are confirmed during Phase 1 setup.
  • Finance posting uses Job Code (FITD_TA_CODE1) and Technician Code (FITD_TA_CODE2); a single labour rate applies to all technicians.
  • Labour KPI definitions and formulation will be provided by the client in the interim.

11. Out of Scope (Phase 1)

  • Customer invoicing of labour (Phase 2 — fixed price & time-and-material).
  • Per-technician cost rates (a single rate card applies in Phase 1).
  • Payroll / attendance integration beyond reading the Employee master.
  • Mobile / field clock-in app (potential later enhancement).

12. Benefits

  • Accurate job cost — labour finally included alongside material and expense.
  • Task-level visibility — actual vs standard hours per task, the basis for true efficiency analysis.
  • Clean finance posting — labour analysed by Job Code & Technician Code, with no extra mapping to maintain.
  • WIP control — unbilled labour visible through job status.
  • Foundation for Phase 2 billing — booked hours feed fixed-price and time-and-material invoicing.
  • No disruption — reuses existing masters, the WO task functionality and the established Job Code linkage.
